## 一、结论速览（TL;DR）

| 诉求 | 结论 | 工作量 |
|---|---|---|
| **让界面显示简体中文** | 官方内置切换入口（`Help → Language → Chinese (Simplified)`），但**简中仅覆盖约 50–65%**，缺号回退英文（2.5 节核实） | **≈ 0**（切菜单，得到部分中文） |
| **独立补丁反馈作者合并（2026-10-18 裁定为优先）** | **C0 独立"简中+繁中补全包"**：双语言缺失清单 + 译文（Blender/Krita 术语参照）+ 管线缺陷证据 + 对比演示——纯数据为主，作者可在源码侧直接吸收 | **约 1–1.5 周**（含演示） |
| 分发版"装完即中文"（预置默认语言） | 可行，预置语言配置文件 | 小（0.5–1 天），前置：真机捕获配置文件格式 |
| 字节补丁（patches.toml）汉化 | **死刑**：等长约束 + 语言串为代码内 lea 引用、无指针表（2.6 节）→ 缺号补齐需逐条代码注入 | 不可实施 |

**最重要的事实**：官方简中是"增量补丁式"维护的**部分翻译**（覆盖率约一半，缺号回退英文）；且语言串在二进制里全部是**代码内硬编码引用**（无指针表）——这同时宣判了字节补丁补缺号的死刑、也决定了上游吸收的正确形态是**译文数据包**而非二进制补丁。最优路径：C0 数据包（主交付）+ C2 shim（演示与验证载体），共享同一份译表。

## 二、实测证据链（全部一手，可复核）

以下证据来自对 Windows PE 的字节级检查与 wine + Xvfb 的实机操作（命令与地址均给出，可独立复现）。

### 2.1 简体中文字符串块内置在 PE 中

```text

0x5f0f08  "曲线辅助"            （= Curve Snap）
0x5f0f60  "为了转换语言，需先关闭应用软件。结束后，请重新启动应用软件。"
```

Linux ELF 交叉验证（同一程序的不同打包）：日文块 `0x865903`（曲線/消失点/…）与简中块 `0x865ec8`（打开图像/曲线辅助/收缩/…）平行存在。主 UI 串区（PE `0x5e0000–0x660000`）内含 CJK 字符串约 **1749 条**（日/简中/繁中/韩多语言混合）。

### 2.2 官方语言切换功能完整接线

- 语言子菜单槽函数（PE 内全部命中）：`onHelpLangAuto` / `onHelpLangEnglish` / `onHelpLangJapanese` / **`onHelpLangChineseSimp`**（0x640061）/ `onHelpLangChineseTrad` / `onHelpLangKo` / `onHelpLangSpanish` / `onHelpLangGerman` / `onHelpLangFrench` / `onHelpLangRussian`
- 菜单项文本（PE 0x636598）：`&English`、`Japanese`、`Chinese (Simplified)`、`Chinese (Traditional)`、`Korean`、`Portugues(e)`…，菜单对象名 `menu_HelpLanguage`（Help → Language 子菜单）
- 语言持久化文件名（PE 0x63d090）：**`Language.ini`**，与 `Config.ini`/`Initialize.ini` 同族（设置文件均在 `%LOCALAPPDATA%\FireAlpaca\FireAlpaca\`）
- 切换确认文案（双语内置）：简中 `0x5f0f60` / 日文 `0x8a1160`（ELF）

### 2.3 wine 实机操作验证（端到端）

在 wine + Xvfb :98 中运行官方 exe 实测：

1. `Help` 菜单完整展开，包含 `Language` 子菜单 ✅（截图存档 /tmp/z_l3.png）
2. 子菜单完整列出 11 项：Auto(默认✓)/English/Japanese/**Chinese (Simplified)**/Chinese (Traditional)/Korean/Portugues/Spanish/German/French/Russian ✅（/tmp/z_le.png）
3. 点击 `Chinese (Simplified)` 后弹出官方确认框："In order to update the language setting, the program will be closed. Please restart the program after closing." ✅（/tmp/z_lf.png）
4. 点 OK 后程序正常退出 ✅

### 2.4 ⚠️ wine 环境实测异常（需真机复验）

点 OK 后**重启程序 UI 仍为英文**，且全盘搜索（`~/.wine`、安装目录、注册表 `HKCU\Software`、`HKLM\Software\FireAlpaca`）**均未发现 `Language.ini` 被写出**（当时只有 `Config.ini`/`NewHistory.ini` 被触碰，内容无语言字段）。

可能解释（按可能性排序）：
1. Xvfb 无窗口管理器环境下自动化点击存在坐标/焦点误差，确认框的 OK 实际未触发（本会话鼠标点击通路曾多次失灵，键盘通路正常）；
2. wine 对该写入路径的虚拟化存在偏差；
3. 程序在"下次启动时"才落盘（与实测不符，但未逐字节追踪其写盘逻辑，不排除）。

**裁定**：语言切换的 UI 链路（菜单→槽→确认框→退出）已验证为官方功能；持久化环节未在 wine 下复现，**应在真机 Windows 上复验**（人工点一次菜单即可，5 分钟）。这不影响"官方内置简中"的结论——字符串与槽函数都在二进制里，缺的只是环境验证。

## 二.5 覆盖度核实（2026-10-18 补充，回应"内置中文但不全"）

**用户观察属实：官方简中是部分翻译，不是完整覆盖。** 两种独立方法定量证实：

### 方法一：平行语言块逐条对比（决定性）

PE 中同一组 UI 字符串（图层/菜单/操作提示区）按语言分块连续存放，块级对比如下
（`injector/cn_coverage_diff.py` 可复现）：

| 语言块 | 位置 | 条目数 |
|---|---|---|
| 日文 ja | `0x5af7d8–0x5afec0` | **37** |
| **简中 zh-CN** | `0x5afec0–0x5b00f0` | **仅 15** |
| 繁中 zh-TW（同区后半） | `0x5b00f0–0x5b06b0` | 41 |
| 韩文 ko | `0x5b06b0–0x5b0d10` | **33** |

> ⚠️ 本表按固定偏移切割，块边界有误差（0x5b00f0 之后实际还有一段简中串被误计入繁中区）。精确数字以**方法三的分组级统计**为准（ja 37 / zh-CN 24 / zh-TW 24 / ko 31，同组）；方法一的定性结论（简中缺号、繁中串混入日文块）不受影响。

该组内简中缺失的条目（有日文/繁中/韩文、无简中）实例：
"4 点点击指定消失点"、"Ctrl+拖拽移动规尺顶点"、"Ctrl+拖拽作成椭圆规尺"、
"拖拽分割/+Shift 自由角度"、"Ctrl+点击指定基点(画布)"、"长按 Ctrl 拖边保持长度平行移动"、
"+Shift 取得画布颜色"、"+Shift 取得显示图层颜色"、"点击选择最上层图层" 等——繁中块（0x5b00f0 后半）里这些**全部有繁中译**，简中块对应位置直接缺号。

**旁证（官方维护方式的缺陷）**：日文块尾部 `0x5afec0` 前混入了 6 条简中
（图层/粘贴/文件夹/边框/滤镜/模板）——官方的简中是"增量补丁式"追加进日文表，
本身就没做过全量对齐，缺漏是结构性的。

### 方法二：全区域语言分类总量（`injector/cn_coverage_scan.py`）

扫描 PE `0x400000–0x700000` 全部含 CJK 的 UTF-8 串并按特征分类：

| 语言 | 条数 | 说明 |
|---|---|---|
| 韩文 ko | 1527 | 最全（基准） |
| 日文 ja | 1302 | 次全 |
| 繁中 zh-TW | 844 | |
| **简中 zh-CN** | **787**（+混合块约一半 ≈ 1050） | **最少** |

以韩文为基准估算，**简中覆盖率约 52%–65%**（平行块抽样低至 ~40%）。

**关键读数**：
- 所有真实 UI 组都**同时缺简中和繁中**（无一组例外），普遍缺 30–50%；

- 简中与繁中的缺号集合高度重叠 → **双语言可由一次翻译派生**（见 4.C0 工作流）。

### 对报告结论的修正

1. **"切菜单即全中文"不成立**——切到简中后，未覆盖的串回退显示英文（Qt tr 机制：无译文时返回源串）。用户在真机看到的"不全"与此吻合；
2. **诉求 A 修正**：切换是 0 成本，但只得到 ~50–65% 中文界面；
3. **诉求 C 的工作量上修**：改进翻译的基线不是"审校官方全量译文"，而是**补齐缺失的 ~35–50%**（简中约 450 条 + 繁中约 400 条，分组级统计见方法三）+ 审校已有部分。shim hook 路线（C2）因支持"未命中回退原文"，是唯一能渐进补齐的方案——补一条生效一条；字节补丁路线（C1）因缺号必须整块重构表结构，**进一步确认不可行**；
4. **C2/C0 工作量修订**：译表提取不能只靠"双语块自动对齐"（简中块缺号导致对不齐），需以英文源串（或日文源串）为键、韩文块为完整性锚、繁中块为参考的人工翻译补齐。**简中与繁中一并生成**（一次翻译派生双语言，见 4.C0），纯翻译投入约 3–5 人日，技术侧（hook+表加载+走查）不变；
5. **附注**：繁中与简中的缺号集合高度重叠——繁中块在字符分类计数中"略多"是假象（繁中串多用非特征字被计入中性类），分组级分析证实两者同量级缺失；因此双语言可由同一份规范化翻译派生，边际成本低。

## 二.6 语言表引用机制核实（独立补丁路线的关键约束）

为评估"独立补丁补齐缺号"的可行性，核实了运行时如何引用各语言串（ELF 上验证，可复现）：

- **无指针表**：`.rela.dyn` 全部 7935 条 `R_X86_64_RELATIVE` 重定位中，指向语言串（`0x865903` 曲線 / `0x8659ec` 折れ線 / `0x865ee5` 曲线辅助）的为 **0**；
- **无文件内绝对指针**：全文件扫描 8 字节小端值等于上述串地址，命中 0；
- **引用方式 = 代码内 rip-relative `lea`**：每条语言串有 1–3 处代码引用（折れ線→`0x623403`，曲線→`0x62b9da`/`0x645e05`，曲线辅助→`0x62165a`）。

**结论**：语言选择是"每字符串 × 每语言"的**硬编码代码分支**（编译器把源码里的字符串表内联成了分支链）。

推论：
1. **纯数据补丁补缺号结构性不可行**——缺失的简中串在代码分支链里**根本没有对应节点**，补上它必须为每条缺失串注入新的代码分支（cave + 分支改链），500–900 条 × 每条一次代码注入，工程上判死。这把 C1 的死刑从"等长约束"升级为"缺号即需改代码"；
2. **对既有条目的等长措辞修正**仍是纯数据操作，可行但价值低；
3. **对上游反馈无影响**——作者有源码，其源码中的字符串表是规整的（编译后才变成分支链）；我们交付**译文数据**即可，作者在自己的表里补条目重建。我们不需要、也不应该去逆向他们的表索引细节来"替作者改二进制"。

## 三、翻译机制的技术定性（决定方案的关键）

对 ELF 的 Ghidra 反编译显示，`tr(ID)` 的实现是：

```c
// dec_CurveSnap_0071b350.c (FUN_0071b350)
QMetaObject::tr(param_1, &QObject::staticMetaObject, &DAT_00965cfd /*源串*/, 0, -1);
```

即 **FireAlpaca 使用 Qt 标准翻译体系**：所有 UI 文本经 `QObject::tr()` → `QMetaObject::tr` → `QCoreApplication::translate` 查询已安装的 `QTranslator`。但有两点与"标准 Qt 程序"不同：

1. **不使用外部 .qm 文件存应用文案**：发行包 `usr/translations/` 里只有 Qt 框架自身的 `qt_*.qm`（30 种语言，含 `qt_zh_CN.qm`），应用文案全部**硬编码进二进制**、按语言分块；
2. 因此 Qt 的 `.qm` 生态工具（lupdate/lrelease）对应用文案**不适用**——这是"改进翻译"方案选型的直接约束。

**推论**：所有运行时替换类方案的正确 hook 点是 `QCoreApplication::translate(const char *context, const char *sourceText, const char *disambiguation, int n)`（Qt5Core 导出符号，`GetProcAddress` 可得）——它是全部 `tr()` 的最终汇聚点，hook 一处即覆盖全应用。

## 四、方案评估（按 2026-10-18 目标重排：独立补丁优先，面向上游反馈合并）

> **目标重定义**：补丁的终局不是"我们长期维护的分发件"，而是**反馈给官方作者（MediBang）合并吸收**。
> 评判标准随之改变：数据可吸收 > 演示有说服力 > 提交格式易合并 > 我们的补丁本身可维护性（吸收后即退役）。

### C0 独立"简中+繁中补全包"（上游反馈导向）—— **本轮列为优先** 🟢

一个**纯数据为主**的贡献包，作者可直接吸收进源码构建：

**范围（2026-10-18 更新）：简中 + 繁中双语言一并生成**——分组级分析（2.5 方法三）证实两者同量级缺失（简中缺 ~450 条、繁中缺 ~400 条），且缺号集合高度重叠，可由一次翻译派生。

| 包内产物 | 内容 | 制作方式 | 工作量 |
|---|---|---|---|
| ① 缺失清单（双语言） | 缺号串列表（以日文源串为键 + 英文对照 + 组/偏移证据），按组分类（颜色菜单、笔刷、图层…） | `cn_coverage_groups.py` 扩展：组级对齐自动生成 | 1 天 |
| ② 简中译文 | 补齐缺失 ~450 条 | **规范化翻译一次成稿**：以 Krita/Blender 简中术语为参照（图层/蒙版/滤镜/笔刷/选区已有社区共识译名），用官方已有简中块统一风格 | 2–3 人日 |
| ③ 繁中译文 | 补齐缺失 ~400 条 | 由简中稿派生：OpenCC s2t + **台湾 UI 词汇替换**（鼠标→滑鼠、文件夹→資料夾、图像→影像、默认→預設、网点→網點…），以 Blender `zh_TW.po` / Krita zh_TW 术语校正 | +1 人日 |
| ④ 术语对照表 | 简中/繁中/日/英四语术语表（约 100–200 核心词），标注与 Krita/Blender/官方已有译名的异同 | 翻译过程中沉淀，CSV+TBX 双格式 | 0.5 人日 |
| ⑤ 技术说明 | 给作者的缺陷报告：语言块布局（组内 ja→zh-CN→zh-TW→ko）、分组缺号统计表（2.5 方法三）、**"ja 块尾部混入 6 条简中"**（其构建管线 zh 表缺口的直接证据） | 本报告 2.5/2.6 节改写 | 1 天 |

**繁中派生的质量要点**：OpenCC 只解决字形，**词汇差异必须人工替换**——台湾 UI 惯用词汇与大陆差异大（滑鼠/資料夾/影像/網點/預設/支援），Blender `zh_TW.po` 与 Krita zh_TW 是现成的、经过社区校对的台湾词汇参照，这正是"采取 Blender、Krita 翻译参考"价值最大的地方（简中术语两库同样可参照，但繁中的词汇级差异更依赖参照库）。

**优点**：零法律风险（译文数据 + 事实性 UI 短语对应关系）；吸收后我们的产物退役、零长期维护；缺号清单本身就是高价值缺陷报告（作者自己未必知道覆盖率）。
**风险**：作者响应意愿与周期不可控（MediBang 官方渠道：官网支持表单/官方论坛/X）；官方可能已有内部翻译流程（无公开信息，需先投递试探）。
**演示件的技术选型说明**：演示**不用字节补丁**——2.6 节已证实缺号补齐需逐条代码注入；用 shim hook（`QCoreApplication::translate`）一天级产出同样的视觉效果，且演示件只服务于"说服作者"，不进入吸收流程。

1. `GetProcAddress(Qt5Core, "?translate@QCoreApplication@@SAPEBDPEBD0H@Z")` 拿到全部 `tr()` 的汇聚点；

## 五、风险与限制

1. **EULA/再分发**：与 snap 项目一致的边界——不分发官方二进制本体；译表/hook 属我们自有产出。官方双语字符串对齐表系从官方二进制提取，公开发布前建议法务再核一次（提取事实性 UI 短语的翻译对应关系，通常风险低）；
2. **wine 异常未解**：2.4 节的持久化问题必须在真机复验；若真机同样无法切换（概率很低），则升格为 bug 级发现，B/C 方案前提重估；
3. **版本漂移**：C1 全量受漂移影响；C2 的 hook 点是 Qt 导出符号（`QCoreApplication::translate` 签名在 Qt5 生命周期内稳定），跨版本鲁棒性最好；译表本身跨版本可复用（源串不变即命中）；
4. **hook 覆盖面**：`QCoreApplication::translate` 覆盖 `tr()` 系；个别硬编码拼接文案（如把数字与单位拼接的）翻译后语序可能不自然——走查阶段处理；
5. **字体渲染**：简中 UI 在无中文字体的环境（wine 无 CJK 字体配置时）可能显示方框——真机 Windows 自带字体无此问题；wine 下需装 `fonts-wqy` 类包。这与汉化本身无关，但影响 wine 里的验证观感。

## 七、可参照的标准、规范与技能生态（2026-10-18 调研）

> 目的：C0 补全包的"交付格式"与"翻译规范"不应自创——对齐业界"明星标准"能提高作者/社区接受度，也降低我们自己的流程设计成本。以下全部经网络核实（2026-10-18）。

### 7.1 翻译数据格式标准（决定交付物格式）

| 标准 | 定位 | 与本项目的适配 |
|---|---|---|
| **GNU gettext（.po/.pot/.mo）** | 开源软件本地化**事实标准**。Blender 官方翻译仓库（`blender/blender-translations`，`po/` 目录含 `zh_CN.po`；GitHub 镜像已归档，主库在 projects.blender.org）、Krita（KDE po 体系）、GNOME 均采用 | **推荐主格式**。 Crowdin/Weblate/Transifex 全部原生导入；作者或其翻译供应商即使没用过也能看懂（源串/译文成对+注释） |
| **XLIFF（OASIS）** | 企业级 CAT 工具交换格式 | 备选；仅当作者方明确使用 CAT 工具链时才需要 |
| **TBX（ISO 30042）/ TMX** | 术语表/翻译记忆交换 | 术语表可作为 TBX 或简明 CSV 双轨交付（CSV 对作者更友好） |
| **ICU MessageFormat** | 占位符/复数/性别处理标准 | 必须遵守其**约定**（即使不用其解析器）：FireAlpaca 大量 `+Shift`/`Ctrl+点击` 组合键串，键名占位必须原样保留 |

### 7.2 中文文案与 UI 翻译的"明星"规范

| 规范 | 位置 | 用途 |
|---|---|---|
| **《中文文案排版指北》**（sparanoid/chinese-copywriting-guidelines） | GitHub，中文文案规范的事实标准（中英文间空格、全角标点、专有名词大小写等） | **译表行文规范**——所有补齐译文按此校对 |
| **W3C《中文排版需求》（clreq）** | `w3c/clreq`（GitHub）+ w3.org/TR/clreq | 排版细节争议时的权威依据（标点挤压、禁则处理等） |
| **Microsoft 简体中文本地化风格指南** | Microsoft Language Portal（各语言 Style Guide PDF + 术语检索） | 软件 UI 语体的大厂标准（菜单动词、控件用语、语气）——FireAlpaca 是 GUI 软件，适配度最高 |
| **Mozilla 本地化风格指南集**（mozilla-l10n/styleguides） | GitHub（CC-BY-4.0，mdBook；各语言社区指南清单在 docs/SUMMARY.md） | 开源社区本地化流程参照（质量门槛、审校流程设计） |

### 7.3 绘画软件领域术语参照（与 FireAlpaca 直接对标）

- **Blender**：`blender/blender-translations`（po + zh_CN）——3D/绘画圈简中术语的共识来源；
- **Krita**：KDE 翻译体系（po），绘画术语（图层/蒙版/蒙板、滤镜、笔刷预设、选区、透明度）的中文译法在 Krita 与 Photoshop 中文社区已高度收敛；
- **方法论**：C0 译表的术语校对应以"官方已有简中块 ∪ Krita/Blender 共识译名"为首选，新词才自创，并随包附**术语对照表**（CSV/TBX）供作者审校——这是提高吸收率的关键细节。

### 7.4 AI agent skill 生态调研（"skill 也可以"）

- 大型合集（`ComposioHQ/awesome-claude-skills` 77k★、`libukai/awesome-agent-skills`、`kntism/skills`、GitHub Copilot skills 规范 `.github/skills|​.claude/skills`）中**均无现成的"软件翻译/本地化"专项 skill**——这是生态空白；

### 7.5 落地到 C0 包的格式决议（建议，2026-10-18 更新为双语言）

1. **交付范围**：**简中 + 繁中双语言**（分组分析证实两者同量级缺失，2.5 方法三）；
2. **交付格式**：gettext PO（主，社区通用；Blender `blender-translations` 即此形态，`po/zh_CN.po` + `po/zh_TW.po` 与本包结构同构）+ CSV（作者易读）双格式，同一份数据生成；
3. **行文规范**：《中文文案排版指北》全量适用；
4. **术语参照**（用户裁定）：以 **Blender / Krita 官方翻译为术语基准**——简中对照 Krita/Blender `zh_CN.po`，繁中对照 `zh_TW.po`（台湾词汇：滑鼠/資料夾/影像/預設/支援…OpenCC 只转字形，词汇必须参照替换）；随包交付四语术语对照表（CSV+TBX）；

6. **skill 固化**：流程做成 agent skill（生态中无现成翻译 skill，自建即填补空白），作为 C0 包的附件一并投递（展示可维护性，提高吸收意愿）。
